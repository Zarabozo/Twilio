# Generator

Turns Twilio's OpenAPI specs into the classes under `lib/Twilio/Rest`. It is for
maintainers, and it isn't part of the CPAN distribution.

The specs are pinned to the `twilio-oai` release in `twilio-oai.version`, and they
aren't kept in this repository. To download them into `spec/`:

    perl tools/fetch-specs.pl

To write the generated classes into `lib/`:

    perl tools/generate.pl

To see what still stops each spec, without writing anything:

    perl tools/generate.pl --report

Generated files start with a comment saying so, and they shouldn't be edited by
hand. `xt/generator/up-to-date.t` fails when `lib/` differs from what the generator
writes.

It also writes a `t/data/contract-*.json` for each spec, which holds what each operation
must send, taken straight from the spec. `t/contract.t` checks the real classes against
them.

Besides the resources, it writes a class for each domain and version, and
`Twilio::Rest::Client`. Only the main API offers a shortcut to each resource of an
account: `$client->messages` is `$client->api->v2010->account->messages`. Elsewhere the
path has the version in it, as in `$client->frontline_api->v1->users`.

## Which specs become code

`Twilio::Generator::Scope` holds three lists, and every spec of `twilio-oai` belongs to
exactly one:

- **Ready** specs are generated. If one stops, generation stops.
- **Pending** specs still have something the generator cannot do. They are named because
  skipping whatever fails would let a spec sync silently delete a whole product.
  `xt/generator/scope.t` fails when a pending spec starts to work, so the list only
  shrinks. Phase 4 ends when it's empty.
- **Excluded** specs are never downloaded, and each one says why. The scope follows what
  the official libraries ship, so check this at each spec sync.

A domain takes twilio-php's name, which isn't always the spec's: `flex` is `flex_api`.

Two specs have no version in their file name, because each holds several. Each first
path segment is then a version, as in twilio-oai-generator: `preview` has
`hosted_numbers`, `marketplace` and `wireless`, and their segments stay in the URL.
`iam_organizations` has `v1`, and its `/Organizations` paths are `versionless`, the
name twilio-php gives them, with nothing of the version's own in the URL.
`Twilio::Generator::Scope` holds that one name.

To print the resource tree of an API:

    perl tools/generate.pl --tree api_v2010

Each line shows a resource, the method that reaches it from its parent, and its
operations:

    Account::Message [messages] list(create list) instance:Sid(delete fetch update)

## How resources are found

These follow twilio-php, which is generated by
[twilio-oai-generator](https://github.com/twilio/twilio-oai-generator). Where a spec is
unclear, twilio-php decides.

- The `parent` in `x-twilio` places a resource, not its path: `SMS/ShortCodes` is a
  direct child of `Account`. A parent need not be part of the path at all: Voice's
  `/Settings` belongs to `DialingPermissions`.
- A path that declares no parent hangs from the version, wherever it is:
  `/Configuration/Addresses` is `AddressConfiguration`, next to `Configuration`. A parent
  written with the version, like `/v1/Roles/{Sid}`, isn't recognized either.
- A declared parent that no path describes becomes a level with no operations. When it
  ends in an id, it takes that id, and its method is named after its class:
  `organization($organization_sid)`, as in twilio-php and twilio-python.
- `className` in `x-twilio` names the class. Without it, `mountName` does: a user's
  `user_channels` are `UserChannel`, not `Channel`. Without either, the last part of the
  list's URL does, even an id: Routes v3's `/ShortCodes/{IsoCountryCode}` is
  `IsoCountryCode`.
- A `mountName` also names the method that reaches the resource, in snake case even when
  the spec writes it in camelCase.
- A key in `dependentProperties` overrides the method name, for the resource at that exact
  URL, ids included.
- One path can hold two resources: `POST` on `Keys` creates a `NewKey`. The spec says so
  with a `className` or `mountName` on the operation itself, and that operation moves to
  a resource of its own. A list and an instance with different names are two resources
  too.
- A path that doesn't say what it is ends in an id when it's an instance. A list can end
  in an id as well, which is part of where the list is.
- An instance path with no parameter at the end is a singleton. A singleton's children
  hang from it.
- When a URL has ids that its parent doesn't hold, the method that reaches it takes them
  first, in the order of the URL: `archived_calls($date, $sid)`. twilio-php sorts them by
  name instead, and this order was chosen on purpose. A URL can also leave out an id of
  its parent, as TaskRouter's `Workers/CumulativeStatistics` does.
- A field's method is its name in snake case: `friendlyName` is `friendly_name`.

The generator stops on anything it can't place, because a guess would become
wrong public API.

## Value types

`Twilio::Generator::Types` says how each format is sent and read, following
twilio-php. A format with no rule stops generation, and `xt/generator/formats.t`
checks every value in every spec in scope, including specs that stop for other
reasons, so a new format shows up there first.

- An array sends each element with its element's rule, as twilio-php's
  `Serialize::map` does.
- A `prefixed-collapsible-map-<Prefix>` is never sent under its own name: each key
  becomes a parameter, as in `AddOns.lookup.Key`.

## What a request takes

- **Headers** are options, as in twilio-php and twilio-python:
  `X-Twilio-Webhook-Enabled` is `x_twilio_webhook_enabled`. An `Authorization` option
  is sent instead of the account's credentials.
- **Query parameters** are options on any operation. A required one comes before the
  options: `read($channel, \%options)`. A list keeps it with the options, so `page`
  takes it there too.
- **A JSON body** is one hash reference, `\%body`, after the required values and before
  the options, with the names Twilio's documentation uses. Its top-level fields have
  rules (dates, and booleans sent as JSON booleans), and any date object deeper in it is
  written as ISO 8601. The owner chose this over twilio-php's model classes.
- **SCIM**: an operation that only answers in SCIM asks for it in `Accept`, as
  twilio-php does.

## Test vectors

`tools/vectors/generate.php` runs real twilio-php and writes what it produces into
`t/data/vectors-*.json`, so the tests compare against twilio-php without needing
PHP. The cases that both languages build are in `tools/vectors/`, and the release
of twilio-php they were last written with is in `tools/twilio-php.version`.

    php tools/vectors/generate.php /path/to/twilio-php

Attributes are sorted in the vectors, because this library sorts them. The text
is otherwise exactly what twilio-php wrote, with two corrections.

## TwiML

`twilio-oai` has no TwiML spec, so the names of elements and attributes come from
the source of twilio-php, in `tools/twiml-elements.json`:

    perl tools/extract-twiml.pl /path/to/twilio-php

Run it again when updating `tools/twilio-php.version`, then run the generator. It
stops on any PHP it doesn't recognize, because a skipped element would simply go
missing.

Two attribute names are corrected there, because twilio-php writes them wrongly
and its tests don't cover them: `for_` becomes `for`, and `xml:Lang` becomes
`xml:lang`. twilio-python uses the corrected names.
